# 项目结构与服务边界

日期：2026-10-23。此文描述当前目录和构建规则，是查看项目结构的入口。

## 1. 从业务域看项目

```text
spring_cloud_test/
├── pom.xml                         总聚合与依赖版本管理
├── gateway/                        HTTP 网关，可独立部署
├── services/                       业务域
│   ├── account/
│   │   └── auth-service/           账号与认证
│   ├── community/

│   │   └── note-service/           社区内容应用

│   │   ├── upload-api/             文件能力契约

│   └── search/
```

根 Maven 只聚合 platform、services、gateway。各层 pom.xml 用于组织构建；独立运行的仍是 7 个 Spring Boot 应用。API 和技术库没有自己的进程、端口或数据库。

## 2. 为什么这样划分

| 归属 | 可部署进程 | 完整业务职责 | 不应承担的职责 |
| --- | --- | --- | --- |
| 接入层 | gateway | HTTP 路由、接入认证、跨域、追踪、入口限流 | 调用业务 Dubbo、查询业务数据库、组装业务详情 |
| 账号域 | auth-service | 注册、登录、第三方绑定、Token、基础账号资料 | 笔记、评论或互动数据管理 |
| 社区域 | note-service | 笔记生命周期、作者权限、评论、互动关系和计数、浏览 | MinIO 存储实现、搜索索引写入 |
| 媒体域 | upload-service | 文件归属、上传与确认、不可变正式对象、签名和临时对象清理 | 决定笔记发布状态 |
| 搜索域 | search-service、search-sync-service | 查询、联想、搜索投影、版本和重建策略 | 修改账号、内容的权威数据 |
| ID 平台 | leaf-service | 唯一 ID 分配 | 账号或笔记业务规则 |

搜索域两个进程分别承担在线查询和异步索引，具有不同的流量与故障隔离需求；它们共用域契约，属于同一业务所有权。评论和互动目前与笔记同进程，通过内部模块隔离，避免在数据与事务边界尚未独立时引入额外网络链路。将来有独立扩容、资源隔离或团队所有权依据时，再把内部模块提升为独立部署。

note-service 的运行名称保留，以兼容现有 Nacos 注册、网关路由、运维配置和端口。其目录归属 community 明确表示它管理整个社区内容边界，而不是只有 note 表。

## 3. 契约与实现一起归属业务域

原先根目录并列的 note-api、comment-api、interaction-api 已合并成 community-api。这三者当前由同一内容应用发布，没有独立的发布周期，单独的 Maven 项目增加了查找和依赖成本。

upload-api 和 search-api 与各自应用放在一起。SearchDocumentEvent 从 common-core 移入 search-api：搜索投影格式属于搜索契约，基础库只保留真正通用的响应类型。未被任何运行模块依赖的 common 兼容聚合已移除。

公开 RPC 接口与 DTO 的 Java 全限定名保留，包括现有 com.example.common 命名空间，保持线上类型和序列化兼容。物理 Maven 归属已经调整；使用旧 note-api/comment-api/interaction-api 坐标的构建，应统一改为 community-api。

安全能力仍分成三个库：Reactive 网关只需纯 JWT 校验；业务 HTTP 服务需要 Servlet 安全；内部调用需要 Dubbo Filter。分别依赖可以避免将 Servlet 或 Dubbo 带入网关，目录上统一放在 platform/security 管理。

## 4. 服务内部按职责组织

服务内部在需要时使用以下角色，不为凑层级创建空目录：

```text
com.example.<service>/
├── <Service>Application.java        启动入口
├── configuration/                  Spring 装配与配置
├── adapter/
│   ├── http/                       HTTP Controller
│   ├── rpc/                        Dubbo provider
│   └── kafka/                      Worker 的消息入口
├── application/                    用例和业务流程
├── domain/                         业务数据模型与算法
└── infrastructure/                 JDBC、ES、认证实现或调度适配
```

社区应用进一步按 content、comment、interaction 划分；各模块内部再分 adapter/application/domain/infrastructure。access 提供目标可访问性接口，integration 负责组合内容、评论的可见性检查。HTTP 和 RPC 共用应用服务，互动应用不直接引用内容或评论 Repository。

账号应用的登录方式分发放在 application/login，Spring Security provider/token/filter 放在 infrastructure/security，账号模型放在 domain，持久化放在 infrastructure/persistence。搜索请求入口在 adapter/http，查询应用门面在 application，ES 查询和索引实现放在 infrastructure/elasticsearch。

这些是职责边界，不要求所有小服务拥有同样数量的层。已有事务、SQL、接口字段和业务行为在本次目录整理中保留。

## 5. 依赖和调用规则

1. 浏览器通过 HTTP 请求 gateway；gateway 通过 HTTP 路由业务服务。
2. 业务服务之间的同步调用使用对方 API + Dubbo，不引用对方可执行应用 JAR。
3. 异步投影使用契约事件 + Kafka；权威写入仍由所属领域负责。
4. 平台模块可以依赖平台契约，不能反向依赖 services 下的业务域。
5. API 项目不引入 Spring Boot、数据库驱动或其他运行框架。
6. 网关只允许引用必要的基础库，不引入业务 API、业务实现或 RPC 安全库。

为这些规则提供了可独立运行的结构检查；它从 Maven 聚合关系读取模块，不再维护另一份路径注册表：

```powershell
python scripts/project_layout.py --check
python scripts/project_layout.py --list-services
python scripts/project_layout.py --service-path note-service
python -m unittest discover -s scripts/tests -v
```

检查涵盖父 POM 定位、重复 artifactId、越界路径、内部依赖是否存在、服务 JAR 互相依赖、API 依赖框架、平台反向依赖业务，以及网关引入 RPC。启动、Nacos 初始化和数据库迁移脚本复用同一个解析器。

## 6. 构建与运行

在仓库根目录执行完整构建：

```powershell
mvn clean verify
```

选择某个应用时使用 artifactId，避免依赖目录深度：

```powershell
mvn -pl :note-service -am test
mvn -pl :search-service -am package -DskipTests
```

生产静态页面仍从 front/dist 拷贝到网关 JAR；前端工程的位置不变。启动脚本会解析服务的新位置，再定位 target 下的可执行 JAR。各应用 Dockerfile 的构建上下文仍是其应用目录，例如：

```powershell
docker build -t live-community/note-service services/community/note-service
```

本次调整保留服务名、端口、RPC 公开类型、Kafka topic 和数据库表；目录变化不引入新的数据迁移。上轮功能修复的存量迁移要求仍见 [实施与部署记录](微服务修复实施与部署.md)。
