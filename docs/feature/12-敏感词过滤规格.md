# 社区文本敏感词过滤：首版规格

日期：2026-10-24。发布日期：2026-10-25。

规格 Issue：[#2](https://github.com/wxb-gs/live_community/issues/2)。标签：ready-for-agent。

本规格依据已确认的讨论整理。业务设计、测试边界和五项纵向任务拆分已确认，按用户继续指令发布。当前未修改功能代码。词库维护与更新、历史内容治理按用户要求暂挂。

## Problem Statement

笔记作者和评论用户可以提交任意文本，当前社区内容应用没有统一的敏感词检查。发布笔记、发表评论或回复时，命中明确禁用词条的内容可能直接公开。

用户需要可解释、可测试的词表过滤：既能识别连续文本中的命中，也能识别特定英文分隔变形；提交失败时应明确说明哪个字段、哪段内容需要修改，并保留输入供用户纠正。检测组件故障必须与词条命中区分，避免误导用户。

过滤行为必须对 HTTP 和内部 Dubbo 调用一致，不能只依赖前端或网关检查。草稿写作不应被公开发布规则打断。

## Solution

在社区内容应用内部提供笔记和评论共用的文本检测能力，由应用层在公开提交的业务流程中调用。

- 笔记草稿允许保存。发布时检查已保存的标题和正文，通过后才执行公开状态变更。
- 根评论和回复在写入可见数据前检查正文。
- 命中后拒绝本次公开提交，保留输入或已有草稿，并在对应输入框下方的错误预览中高亮原文片段。
- 中文和英文连续文本均按子串匹配。英文额外支持明确列举的独立单字母分隔变形，不把正常英文单词任意拼接。
- 检测故障时阻止本次公开提交，返回可以重试的独立错误，不将故障说成词条命中。

首版关注确定性的文本规则，不进行语义审核，也不自动改写用户内容。

## User Stories

1. As a note author, I want to save a draft containing a configured word, so that publication rules do not interrupt private writing.
2. As a note author, I want the saved title checked when publishing, so that a configured word in the title cannot become public.
3. As a note author, I want the saved body checked when publishing, so that a configured word in the body cannot become public.
4. As a note author, I want rejected publication to leave my draft intact, so that I can correct my writing without losing it.
5. As a commenter, I want my comment checked before it becomes visible, so that configured words are rejected consistently.
6. As a person replying to a comment, I want replies checked by the same rules, so that replying cannot bypass filtering.
7. As a commenter, I want rejected submission to preserve my input, so that I can edit and submit it again.
8. As a person replying to a comment, I want rejected submission to preserve my reply text and reply target, so that I can continue the same conversation.
9. As a user, I want Chinese words detected inside longer continuous text, so that matching does not depend on spaces or segmentation.
10. As a user, I want English words detected inside longer continuous text, so that longer words, numeric suffixes, or surrounding underscores do not bypass the configured rule.
11. As a user, I want English letter case normalized for detection, so that changing case does not change the result.
12. As a user, I want fullwidth ASCII equivalents normalized for detection, so that changing character width does not bypass a match.
13. As a user, I want the original text retained during normalization, so that filtering does not silently rewrite my writing.
14. As a user, I want separately written English letters checked as an allowed spelling variant, so that forms such as b-a-d and b a d can be detected.
15. As a user, I want underscores and periods supported in that spelling variant, so that b_a_d and b.a.d are handled consistently.
16. As a user, I want tab-separated single-letter variants handled consistently, so that a tab does not bypass the allowed separator rule.
17. As a user, I want normal English words kept separate during variant detection, so that a phrase such as job advertisement is not accidentally reconstructed into a configured word.
18. As a user, I want partially split forms outside the agreed single-letter rule left unmatched by that rule, so that the initial behavior remains explicit and predictable.
19. As a user, I want newline characters to remain boundaries, so that filtering does not reconstruct words across lines.
20. As a user, I want slash, Chinese punctuation, and zero-width characters kept outside the separator rule, so that the system does not silently apply broader transformations.
21. As a note author, I want the title and body checked independently, so that their adjacent ends are not combined into a fabricated match.
22. As a community user, I want separate comments and replies checked independently, so that text from different submissions is never combined.
23. As a user, I want quotation, negation, and educational context handled by the same literal rules, so that the first version does not claim to infer my intent.
24. As a user, I want a rejection to identify the affected field, so that I know which part to edit.
25. As a user, I want matched original text highlighted in an error preview, so that I can locate the problem without replacing the editor.
26. As a user, I want my text preserved instead of automatically replaced with asterisks, so that I remain in control of its wording.
27. As a user, I want the preview limited to 20 match locations, so that a heavily matching input does not produce an unbounded error display.
28. As a user, I want an indication when additional matches exist, so that I understand the preview may not list every problem.
29. As a user, I want any match to reject the submission even when the preview is truncated, so that the display limit does not become an acceptance limit.
30. As a user, I want detection failures distinguished from word matches, so that I know whether to edit my text or retry later.
31. As a user, I want temporary detection failure to preserve my input, so that an unavailable component does not destroy my work.
32. As a community operator, I want detection failure to prevent public submission, so that an unavailable component does not silently bypass the agreed check.
33. As an internal service caller, I want the same application checks as an HTTP caller, so that using Dubbo does not bypass filtering.
34. As a maintainer, I want rejected publication to preserve the public state and publication-related events, so that rejection does not partially publish content.
35. As a maintainer, I want rejected comments to leave comment content, indexes, and counters unchanged, so that filtering failure does not create inconsistent records.
36. As a maintainer, I want matching tests supplied with an explicit fixed word list, so that results are deterministic without deciding the deferred production dictionary management design.

## Implementation Decisions

### 归属与调用

- 能力归属于社区域的 note-service，笔记与评论共用检测组件，不新增独立过滤微服务。
- 笔记发布与评论创建应用入口负责调用检测。HTTP 与 Dubbo 适配器继续复用应用入口，网关不承担权威检测职责。
- 输入为本次操作对应的文本字段及一份明确词表。匹配能力与词表供给解耦；本规格不指定文件、数据库、配置中心或管理后台作为生产供给方式。
- community-api 仅在需要承载对调用方可见的错误契约时调整。通用响应和错误适配只修改必要的结构，不将敏感词业务逻辑放入公共安全库。
- 当前只有普通文本笔记与评论，未发现需要一并实现的独立文档服务或富文本处理流程。

### 检查时机与一致性

- 创建或保存草稿不执行公开拒绝规则。
- 发布检查针对服务端实际保存的标题和正文，不能仅检查前端额外传入的副本。
- 保留现有身份、作者和状态校验，不通过新的错误详情向无权调用者暴露内容或检测结果。
- 只有检测通过后才允许笔记变为公开状态并产生相应发布投影；被拒绝的笔记保持原有草稿。
- 根评论和回复在可见数据写入前检查；被拒绝时，不留下新增的评论索引、正文或主题计数变化。
- 现有草稿可能已经产生非公开搜索投影。拒绝发布的验收应比较发布操作前后是否新增公开状态或发布事件，不应错误要求历史 Outbox 为空。
- 实现需要保证真正发布的文本就是通过检查的文本；若引入并发编辑，不能出现检查旧版本而发布新版本的绕过。

### 匹配规则

1. 中文连续文本使用子串匹配，不要求先分词。
2. 英文连续文本同样使用子串匹配，不要求完整单词边界。此前讨论过的英文完整单词限制已经被用户明确撤销。
3. 在检测副本上统一英文大小写和全角 ASCII 宽度差异；不改变保存与显示的原文。
4. 不进行完整兼容归一化的额外折叠，例如不额外将圈号数字变成普通数字；不进行繁简、拼音、谐音或近形字转换。
5. 英文分隔变形只识别独立单字母组成的拼写。允许普通空格、制表符、英文连字符、下划线和英文句点作为间隔。
6. 不将正常英文单词任意去空格后拼接，也不使用删除所有非文字字符的宽泛规则。
7. 部分分割形式不属于首版独立单字母变形规则，例如 ba d 和 b ad。
8. 英文分隔变形不跨换行；斜杠、中文标点和零宽字符不被该规则忽略。
9. 中文仍仅做连续子串匹配，不因本次增加英文变形识别而扩大为中文分隔变形检测。
10. 标题、正文、每条评论和回复独立检查，不跨字段或不同提交拼接。
11. 无语义判断、上下文豁免或白名单豁免。引用、否定和教学场景同样适用上述匹配规则。
12. 未决定必须使用 AC 自动机、Trie、正则或某个第三方库。实现应以满足可观察规则和测试为准，不能把效率算法包装成语义理解。

### 可观察匹配样例

下列英文样例均使用词条 bad，仅用于确定性验收，不代表生产词库内容。

| 输入 | 结果 | 原因 |
| --- | --- | --- |
| bad、BAD、ｂａｄ | 命中 | 连续文本及明确归一化 |
| 很bad、bad！ | 命中 | 连续子串 |
| badminton、bad123、_bad_ | 命中 | 英文不再要求完整单词 |
| b-a-d、b a d、b_a_d、b.a.d | 命中 | 允许的独立单字母变形 |
| 各字母之间为制表符 | 命中 | 制表符属于允许间隔 |
| job advertisement | 不命中 | 不拼接正常英文单词 |
| ba d、b ad | 不命中 | 不属于独立单字母变形 |
| b/a/d、b，a，d | 不按分隔变形命中 | 分隔符不在允许清单 |
| 字母跨换行或被零宽字符隔开 | 不按分隔变形命中 | 不忽略对应字符 |

上述“不按分隔变形命中”不取消独立存在的连续子串命中。若一段输入同时包含这些形式和真实连续的 bad，仍应拒绝。

中文样例使用词条“测试词”：正文“这里有测试词”应命中；标题末尾“测试”与正文开头“词”分别不命中；“测-试-词”不因英文变形规则被重构为命中。

### 错误契约与前端

- 至少区分可由用户修改的词条命中错误，以及可重试的检测故障。具体 HTTP 状态、业务码或异常类名称属于契约细化，不在本规格中冒充已由用户选定的固定值。
- 命中详情需要表达字段、原文命中区间、预览所需片段，以及是否还有更多命中。详情不能只指向去间隔或归一化后的文本，否则前端无法准确高亮。
- 原文区间的坐标单位与起止语义必须在 Java 和前端之间一致，并用全角字符、制表符和非 BMP 字符场景验证，避免高亮偏移或损坏原文。
- 一次最多展示 20 处命中位置，超出时显示还有更多。任何命中都拒绝提交；展示上限不是最多检查 20 个位置。
- 保留现有输入框，在下方错误预览中高亮。无需为此引入富文本编辑器，不将用户内容替换为星号。
- 请求封装需要保留可预期非成功响应中的业务详情，同时保留现有认证失效和限流处理。
- 评论和回复需要补可见错误反馈；不能仅让 Promise 拒绝而不向用户说明原因。
- 检测故障不生成词条命中详情，提示检测暂时不可用、可以稍后重试，并保留输入或草稿。
- 不向用户返回完整词库；高亮预览按文本安全渲染，不把提交内容当成 HTML 执行。
- 不要求新增审核表、待审状态或审核后台。是否需要其他持久化结构不作为已定方案，不能借本功能擅自创建词库或审计管理系统。

## Testing Decisions

以社区业务应用入口为主要测试边界，辅以必要的传输契约和界面验收；不新增产品边界。

### 主要测试边界：社区业务应用入口

- 以笔记发布、根评论创建和回复创建的应用入口作为主要行为测试边界。这里是 HTTP 与 Dubbo 共用的最高业务层，适合验证检查是否真正阻止公开写入。
- 测试使用真实检测能力和显式测试词表，不模拟检测结果来代替规则验收。只隔离 Leaf、对象存储及外部消息投递等与匹配规则无关的系统。
- 优先延续 PublicationTest 的应用入口测试方式，以及 BoundaryPersistenceTest 的真实事务与持久化状态断言方式。
- 只断言返回结果、公开状态、数据库变化和发布相关事件等外部可观察行为，不锁定自动机节点、内部扫描次数、私有方法或具体算法。
- 以参数化案例覆盖上述连续匹配、归一化、英文单字母变形、不支持的分隔符、正常短语和跨字段边界。无需在每层重复整套词表矩阵。
- 成功样例与拒绝样例都要有。检查命中或检测故障后，笔记仍未公开，评论和回复没有新增可见记录或计数变化。
- 身份、作者权限、目标可访问性等原有业务测试继续通过。

### 少量契约与界面补充

- 参考项目已有 WebMvcTest 鉴权与响应测试，补充结构化错误的 HTTP 契约验收。
- 验证 HTTP 和 RPC 适配器都经过相同应用入口，不允许任一入口绕过；不为此给每种传输复制一套匹配算法测试。
- 在发布、评论和回复界面验证命中详情展示、原文区间高亮、输入保留、故障提示，以及超过 20 处的截断提示。
- 当前前端没有现成自动交互测试脚本。优先围绕这些用户交互补最小可用验证，不将新建整套端到端平台作为本功能前置任务，也不预先指定尚未讨论的测试框架。

## Out of Scope

- 词库的实际内容、运营归属、存储介质、维护方式、版本发布、热更新和多实例词库同步：用户明确暂挂，不能默认选择文件、数据库、配置中心或后台。
- 历史内容扫描、重审、修改、删除和下架：用户明确暂挂，不在本规格中制定历史治理政策。
- Word、PDF 等附件正文提取；图片 OCR；昵称、账号资料、私信等未纳入的文本字段。
- 独立过滤微服务、跨业务域共享审核平台。
- 语义分类、大模型审核、上下文豁免、人工待审与申诉工作流。
- 拼音、谐音、繁简转换、近形字符及广泛 Unicode 兼容折叠。
- 中文插入分隔符的变形识别、任意删符号匹配，以及对所有混淆表达都能识别的承诺。
- 自动替换原文、修改既有公开内容或升级为富文本编辑器。
- 借本功能重做笔记草稿编辑/重试复用流程、修改评论长度上限或调整现有文件上传生命周期。
- 未经实测的 QPS 或延迟承诺；将算法名称作为功能完成标准。

## Further Notes

- 用户已确认业务设计基线；本规格合成阶段不重新访谈已定业务问题。
- 测试边界与五项纵向拆分已随继续发布指令确认。各项任务都包含自己的行为测试，不将测试统一推迟到最后。
- 生产词表供给尚未决定。检测能力及错误链路可以用显式提供的测试词表设计和验证，但不能因此宣称真实生产词库已经接入或擅自补一套管理方案。
- 当前仓库发布时只提交笔记引用，服务端读取已有草稿文本；不应增加一个仅检查前端预检结果的旁路。
- 当前笔记发布界面在重试时可能重新创建草稿。本规格要求保留输入，不以顺手重做草稿复用机制扩大范围。
- 现有通用请求封装会丢弃大部分非成功响应的业务详情，评论失败没有可见提示；这是实现已确认交互时必须补齐的接入工作。
- 当前项目没有发现专用领域词汇表或此处相关 ADR，沿用现有“笔记、草稿、发布、根评论、回复、社区域、应用入口、Outbox、公开投影”等术语。
- 规格与任务发布到 wxb-gs/live_community 的 GitHub Issues，使用 ready-for-agent 标签。任务以真实 Issue 标识建立依赖；生产词库接入和历史治理仍需后续单独约定。
