# 微服务边界与一致性修复方案

日期：2026-10-22

状态：代码及迁移工具已实施，本地验证见 [实施与部署记录](微服务修复实施与部署.md)。本文保留原始目标与最终部署验收项；未完成的真实环境检查不勾选。

## 1. 范围与基线

本方案针对当前工作区的实际实现，覆盖微服务职责、发布授权、文件生命周期、互动一致性、浏览计数、搜索同步、数据隔离、公共契约及架构文档。当前工作区已有评论迁移等未提交修改，实施前应保存基线，保留这些修改，禁止以重置工作区的方式推进本方案。

最初评估只生成本文；后续实现已修改业务代码及配置并增加迁移工具。本地验证与设计取舍见实施记录；没有对当前部署执行迁移或压测，最终验收项仍需真实环境验证。

原则：先修正确性和内部边界，再按扩容、故障隔离、团队职责决定独立部署；不以增加服务数量作为完成标准。

架构约束：优先采用普通 HTTP 网关。外部链路为“前端 → Gateway → 业务服务 HTTP Controller → 应用服务”；业务服务之间的同步调用使用 Dubbo，异步通信使用 Kafka。网关不作为 Dubbo 消费者，不承接页面数据聚合。

## 3. 目标服务与数据边界

| 服务或模块 | 拥有的职责与数据 | 边界约束 |
| --- | --- | --- |
| gateway | HTTP 路由、接入认证、限流、跨域、追踪标识 | 不调用 Dubbo，不聚合业务数据，不读写领域存储，不决定发布状态 |
| auth-service | 注册、凭证、第三方绑定、Token、基础账号资料 | 暂不独立 user-service；不承接内容和互动逻辑 |
| note-service：笔记模块 | note、发布状态、作者关系、文件引用、浏览数据 | 资源权限在本域验证 |
| note-service：评论模块 | comment_index、comment_content、comment_subject | 保持本地事务；不直接引用笔记 Repository |
| note-service：互动模块 | interaction_record、互动权威计数、命令幂等记录、事件 Outbox | 第一阶段仍同进程，禁止直接更新 note/comment 表 |
| upload-service | 文件元数据、对象 Key、上传确认、签名、访问规则 | 内容只引用 fileId；存储密钥仅由文件能力持有 |
| search-service + search-sync-service | 搜索查询、索引契约、索引投影及重建 | 同属搜索域，可分别部署查询进程和 Worker |
| leaf-service | ID 分配及号段元数据 | 保证唯一性；不决定业务状态 |

第一阶段不新增 comment-service、feed-service、user-service。互动模块只有在一致性修复、契约隔离和性能验证完成后，才作为优先候选独立部署。

## 4. R01：身份与资源授权

涉及：网关认证过滤器与路由、各业务服务 HTTP Controller、common/PublishNoteRequest、NoteRpcService、note/rpc/NoteRpcServiceImpl、NoteService。迁移期间同时覆盖旧 gateway/controller/NoteController。

实施步骤：

1. 网关校验访问 Token，并清除客户端伪造的身份 Header。业务服务优先独立验证透传的 Token，从本地认证上下文获取 actorUserId，不接受请求体声明操作者身份。若采用网关签名身份上下文，必须验证签名、有效期和调用方身份，不能信任明文 Header；Dubbo 显式传递可信调用上下文。
2. 发布时由 NoteService 验证 note.userId == actorUserId，并采用带作者和旧状态条件的更新，检查受影响行数，防止检查与写入之间的并发覆盖。
3. 无身份返回 401，无权限返回 403，状态冲突返回 409。HTTP 与 RPC 的异常映射保持一致。
4. 下游 HTTP Controller 是网关的正式路由目标，必须补齐认证和业务授权；额外调试入口移除或默认关闭。业务端口部署于内网，直接访问仍须认证。内部 RPC 通过网络隔离和服务身份验证限制调用者，不能仅凭任意客户端传入的 userId 信任身份。HTTP 和 Dubbo 适配器调用同一应用服务，避免分别实现业务规则。
5. 补齐草稿读取、评论和互动目标可访问性规则，公开查询不泄露他人草稿。删除、封禁内容的缓存失效与目标校验由所属领域提供。

验收：作者可发布；其他登录用户不可发布；伪造请求体 userId 无效；直接调用下游入口不可绕过；并发发布只发生一次有效状态转换。

## 5. R02、R06：统一文件生命周期

目标流程：创建草稿 → 申请上传 → 前端直传 → 文件确认 → 发布笔记。

新增文件元数据（由 upload-service 管理）：fileId、ownerId、objectKey、purpose、绑定资源、声明/实际大小和类型、状态、expiresAt、version。状态至少包含 PENDING、READY、EXPIRED；note 保存 fileId，历史 objectKey 作为迁移兼容字段。

拟定接口：

| 接口语义 | 关键输入 | 结果 |
| --- | --- | --- |
| prepareUpload | actorUserId、purpose、资源引用、文件声明 | fileId、PUT URL、过期时间 |
| confirmUpload | actorUserId、fileId | 校验对象存在、实际大小、允许类型及归属，返回 READY |
| publishNote | actorUserId、noteId、fileId、requestId | 绑定已确认文件，返回发布后快照 |
| resolveFiles | 可访问的 fileId 集合 | 批量访问地址或稳定资源地址 |

确认不能只信任前端的“上传成功”；需要检查实际对象。READY 文件应不可被旧 PUT URL 再覆盖，可通过临时对象提升为不可变正式对象等方式实现。签名和 fileId 不可成为跨用户复用授权。

发布前完成远程文件校验，再在本地事务内更新笔记和写入搜索事件 Outbox；不得在持有数据库锁期间等待 MinIO。文件绑定必须幂等，若要求单次绑定，需要文件侧预留/确认协议和超时补偿，禁止假设两个服务共享事务。孤儿文件只在排除有效引用或预留后清理。

迁移时使用新上传/发布接口，前端同步改为分阶段调用；旧发布接口不再保留“签名即发布”的行为。历史 objectKey 按可重复脚本补充元数据，缺失对象生成核对清单，不自动删除历史笔记。

验收：未上传、上传失败、过期、超限、他人文件均不能发布；确认和发布重试不产生重复绑定；并发发布不覆盖；返回状态为持久化后的 PUBLISHED；详情和列表批量解析文件，note-service 不再持有 MinIO 密钥和路径生成规则。

## 6. R03、R04：互动持久化与计数一致性

本方案选择 MySQL 关系状态和计数为权威源，Redis 为可重建缓存。先确保正确性，保留现有 Redis-first 路径作为默认实现会继续存在 Redis/Kafka 双写窗口。若压测证明同步持久化不满足目标，再单独设计持久日志优先的异步命令方案。

1. 将 toggle 改为“设置目标状态”：输入 requestId、actorUserId、targetType、targetId、interactionType、desiredActive。网络重试复用 requestId，不再次反转状态。
2. 关系唯一键为 targetType + targetId + interactionType + userId。通过锁或条件更新，在本地事务内读取旧状态，计算 delta = newActive - oldActive，仅真实状态变化更新权威计数。
3. 同一事务写入幂等结果及 Outbox。事务提交后异步刷新 Redis、发送 Kafka；发送失败持续重试，进程重启后继续处理。
4. 移除当前“内存窗口为持久化中间站”的机制。snapshot 后 clear 可能丢失并发新增事件，提交消费位点早于数据库持久化也会造成丢失，不能仅靠加锁修复整体可靠性。
5. 事件包含 eventId、schemaVersion、聚合标识、单调 version、occurredAt、绝对计数和关系变化。多个客户端的请求顺序以持久化版本为准，不用客户端时间戳决定新旧。
6. 笔记和评论投影分别消费事件，只更新自己的表；以版本条件更新绝对计数，不重放裸 +1/-1。领域计数投影字段只允许对应消费者维护，避免多个写入源覆盖。
7. 消费者在持久化成功后确认；失败抛出明确异常，按策略重试并进入可重放的失败队列。设置告警和修复入口，不以打印日志作为恢复措施。
8. Redis 丢失时由权威状态批量重建；定期对账关系、权威计数和投影，禁止简单把缓存缺失解释成真实零值。

验收：未点赞→点赞→取消净变化为零；重复设置同一状态无变化；重复事件、旧事件晚到不会重复累计；事务前后宕机、Kafka 故障、缓存清空均可恢复；评论点赞关系也持久化；作者删除内容后按明确策略拒绝新互动并清理历史投影。

迁移：暂停旧写路径，排空并记录旧消费者进度，核对 Redis、interaction_record 和现有计数。评论关系若仅存在 Redis，应在缓存仍可读取时导出；不可恢复的数据列为差异，不凭现有计数伪造用户关系。完成回填和校验后切换新路径，禁止双消费者同时累加。

## 7. R05：浏览计数归属和恢复

浏览量定义为成功公开详情访问次数，允许同一用户重复访问；接口重试的去重范围必须在测试中固定。若要统计独立访客，另行设计，不混用现有计数。

网关移除 note:view:* 写入，由内容域记录。第一阶段可保留 Redis 暂存，但必须声明持久化假设：已落入持久化浏览日志的事件可重放；日志前故障是否允许丢失及容忍量需要记录，不能宣称端到端零丢失。

实现采用带 eventId 的持久化访问日志或等价可靠队列，按批次累计；MySQL 在同一事务写入 processed_batch 唯一批次和计数。数据库成功后再确认批次，重放命中唯一键即跳过。停止使用 KEYS 全量扫描，以及 GETDEL 后数据库失败无补偿的流程。临时保留 Redis 计数时，以可恢复 pending 批次替代删除即结算，并明确 Redis 持久化配置和故障损失范围。

验收：数据库异常后批次仍可重放；持久化成功但确认前宕机不重复加量；多实例并行不重复结算；失败访问和草稿访问不计入公开浏览量；使用 long/BIGINT 避免计数转换溢出。

## 8. R07：统一搜索变更来源

目标选择“业务事务 Outbox → Kafka → 搜索 Worker”，停用 Canal 对相同业务表的直接索引投递。Canal 如保留为学习演示，应使用独立 profile/topic/index，不写生产目标索引。不得直接移除唯一用户同步来源：账号域也必须实现用户资料变更 Outbox 后再关闭原链路。

1. 发布、编辑、删除以及需要同步的计数投影更新，均与搜索 Outbox 写入在同一本地事务完成；账号域同理。
2. 逐步替换 NoteSyncProducer 的 Canal 行格式，建立包含 entityType、entityId、version、schemaVersion、operation 和完整索引投影的契约。按实体分区，消费者仍以版本拒绝旧事件。
3. 单实体索引版本由所属领域维护，标题、状态、计数等影响投影的变化都推进版本，避免只给部分事件编号。
4. 删除使用可比较版本的墓碑或等价持久化删除版本机制，避免延迟更新使已删除文档复活；草稿、封禁内容不进入公开结果。
5. SearchSyncConsumer 失败时进入明确重试流程，不依赖“未 ACK 就必定马上重投”的假设。覆盖异常、失败返回、毒消息、部分批量成功等情况。
6. 提供全量重建命令：记录变更水位、加载公开投影快照、追平增量、核对数量及抽样字段，再原子切换索引别名。新旧索引保留回滚窗口。

验收：Canal 与主动生产不会同时覆盖正式索引；创建、发布、编辑、取消公开和删除最终正确；同实体乱序消息不能回退版本；ES 宕机恢复后可追平；用户搜索持续同步；全量重建期间的新增修改不丢失。

## 9. R08—R11：模块、数据库和基础设施收敛

### 9.1 内部模块

note-service 先按 note、comment、interaction 组织 api/application/domain/infrastructure，跨模块仅调用公开应用接口或订阅事件。评论的 index/content/subject 写入加入本地事务。笔记详情的评论和互动属于可降级聚合数据，设置明确超时；拆出后采用批量 API，防止逐条 RPC。

独立 interaction-service 的前置条件：无跨域 Repository 引用、独立数据权限、缓存可重建、Outbox/消费者可恢复、接口兼容测试通过，并有扩容或故障隔离证据。达到条件后再迁移数据和部署；评论继续同进程运行。

### 9.2 数据权限

先保留单 MySQL 实例，通过独立账号授予表级权限。auth 仅管理账号表，note/comment/interaction 模块分别登记表归属，upload 管理新增文件表，leaf 管理发号表。Outbox 和幂等表由各自领域管理。生产运行账号禁止 DDL，迁移账号独立；配置同时检查本地 YAML、Nacos 初始化脚本、容器和部署文档。

验收以越权 SQL 被拒绝为准，不能仅检查配置中是否换了用户名。后续独立实例迁移不得引入跨库 JOIN。

### 9.3 契约与普通 HTTP 网关

将 common 渐进拆为 common-core、note-api、comment-api、interaction-api、upload-api、search-api、leaf-api 及领域事件契约；不要求一次性拆完。移除契约模块的 spring-boot-starter-web，按实际使用显式声明轻量依赖，应用自己声明 Web starter。兼容旧 DTO 的迁移期、调用方升级顺序和序列化 schema 都需记录。

gateway 迁移为 Spring Cloud Gateway 路由应用，通过 Nacos 服务发现定位 HTTP 下游。路由统一为 `/api/auth/**` → auth-service、`/api/note/**` 与 `/api/interaction/**` → note-service、`/api/upload/**` → upload-service、`/api/search/**` → search-service。路径尽量保持现有前端契约；确需重写时在路由中显式配置并测试。互动独立部署后只调整目标服务。

实施顺序：

1. 先补齐业务服务的 HTTP 接口。目前 note 的下游 Controller 缺少网关承接的部分评论及列表接口，interaction 缺少独立 HTTP 适配器，search 使用 internal 路径且能力不完全一致；逐项对照现有网关接口补齐方法、参数、身份、响应、错误码和分页语义。
2. HTTP Controller 调用本服务应用层。原先只在 RPC 实现中的逻辑提取到应用层供 HTTP/RPC 复用。详情聚合在所属应用服务完成，必要时批量调用内部 Dubbo；不在网关增加聚合 Controller。
3. 选用与项目依赖兼容的 Gateway 运行栈，替换当前 MVC 手写转发。若使用响应式 Gateway，认证改用对应的响应式安全过滤链，移除 Servlet Controller 和冲突的 MVC 依赖；common 去除 Web starter 是该路径的前置任务。
4. 启用路由并逐项切换，移除网关中的 Note/Interaction/Search/Upload Dubbo Controller 和 AuthProxyController。网关不再依赖领域 RPC API、Dubbo starter、MinIO SDK 或业务 Redis 操作；认证确需的 Redis 使用须与领域数据写入区分。
5. 网关统一认证、限流、跨域、连接/响应超时和追踪标识；服务保留业务错误语义。写请求禁止透明重试，只有具备幂等保证的操作才配置重试。浏览计数等副作用随职责迁移至业务服务。
6. 前端静态资源和 MinIO 路由可以保留为纯 HTTP 转发或迁至独立静态入口，不增加领域逻辑。按实际上传、签名 URL、请求体大小和跨域需求验证转发行为。

验收：前端公开 API 路径兼容；网关无 Dubbo 引用、业务 Controller 和领域存储写入；所有路由经服务发现访问下游；下游 HTTP 接口认证及授权完整；业务服务间 Dubbo 调用正常；限流、超时、跨域、上传及错误透传验证通过。

### 9.4 ID 服务

先保留 leaf-service。业务侧评估批量号段客户端，禁止每次号段内发号都新增网络请求。号段缓存必须保证多实例和重启不重用，未耗尽号段允许浪费；雪花方案必须具备节点号分配和时钟回拨处理。Leaf 不可用时按业务明确快速失败或消耗已分配号段，不允许临时生成可能冲突的 ID。

验收：多实例唯一性、重启唯一性和依赖故障测试通过；未测得实际收益前不强制更换算法。

## 12. 上线、回滚和最终验收

数据库变更采用先加字段/表、回填、切读写、最后移除旧字段的顺序。备份和差异对账先于任何权威源切换。事件升级先部署兼容消费者，再部署新生产者；同一业务禁止旧新路径重复结算。

回滚保留前端及接口兼容窗口、旧索引别名和消费水位。切换权威数据源后不能仅回退二进制：必须停止相关写入，处理新路径积压并对账，再恢复旧路径。禁止为兼容旧版本重新开放越权发布或未确认上传即发布。
